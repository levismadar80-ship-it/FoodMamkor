# Pass the PR author to the mention guard, and (if wanted) make the closing-line rule block — YAML patch for `pr-checks.yml` (MEH-2244 chunk A)

> **The blocks here are for Sapir to apply by hand.** `.github/workflows/**` is
> CC-deny (`.claude/settings.json`, MEH-671) — CC writes the diff into this `.md`
> and does not touch the workflow. **Nothing here has been applied.**
>
> The script half ships in the same PR as this doc: `check-linear-mentions.sh`
> now requires the PR **body** to carry, as a standalone line, either
> `Closes MEH-<N>` or `Refs MEH-<N> (chunk <k>/<n>)`, exits **3** when it does
> not, exempts dependabot by author, and its `--self-test` covers every case in
> §3. Only the wiring is left, and hunk 1 is the only part that is *needed*;
> hunk 2 is a decision.

Same job, same shape, and same precondition as
[`meh-1949-branch-arg-wiring.patch.md`](./meh-1949-branch-arg-wiring.patch.md):
both feed one more input to the same script, and both are pointless until that
doc's **hunk 2** widens the job's `if:` — see §4.

## 1 · Where the job is today

`pr-checks.yml:722-739` on `origin/staging` at the time of writing (line numbers
from `git show origin/staging:.github/workflows/pr-checks.yml`):

```yaml
  linear-mentions:
    name: Linear mention guard (rule 29, warn-only)
    needs: changes
    if: ${{ needs.changes.outputs.frontend != 'true' && needs.changes.outputs.backend != 'true' && needs.changes.outputs.workflows != 'true' }}
    runs-on: ubuntu-latest
    timeout-minutes: 5
    continue-on-error: true                                   # :728
    steps:
      - uses: actions/checkout@v7
      - name: Write PR title and body to files
        env:
          PR_TITLE: ${{ github.event.pull_request.title }}
          PR_BODY: ${{ github.event.pull_request.body }}
        run: |
          printf '%s' "$PR_TITLE" > "$RUNNER_TEMP/pr_title.txt"
          printf '%s' "$PR_BODY"  > "$RUNNER_TEMP/pr_body.txt"
      - name: Check for bare Linear identifiers (warn-only)
        run: bash .claude/scripts/check-linear-mentions.sh "$RUNNER_TEMP/pr_title.txt" "$RUNNER_TEMP/pr_body.txt" || true    # :739
```

Two things swallow every finding: the `|| true` on the step (`:739`) and
`continue-on-error: true` on the job (`:728`). With both in place the new check
**prints** — a `::warning::` annotation plus a whole-word `WARNING` line — and
**blocks nothing**. That is the state the script was written for; whether it
stays that way is hunk 2.

## 2 · Hunk 1 — pass the PR author (`:739`)

The script reads the author from the `PR_AUTHOR` environment variable (or a 4th
positional argument). The env form is used here so this hunk composes with
MEH-1949's hunk 1 in either order: neither has to know whether the other added
a positional argument.

```diff
       - name: Check for bare Linear identifiers (warn-only)
+        # MEH-2244: the PR author, for the dependabot exemption on the
+        # closing-line check. Via env, never interpolated into `run:` — a
+        # login is attacker-controlled on a fork PR and `${{ }}` inside `run:`
+        # is substituted before the shell sees it. Same discipline the step
+        # above already applies to the title and body.
+        env:
+          PR_AUTHOR: ${{ github.event.pull_request.user.login }}
         run: bash .claude/scripts/check-linear-mentions.sh "$RUNNER_TEMP/pr_title.txt" "$RUNNER_TEMP/pr_body.txt" || true
```

If MEH-1949's hunk 1 is applied first, the step already has an `env:` block
(`PR_HEAD_REF`); add `PR_AUTHOR` as a second key under it rather than a second
`env:`.

**Without this hunk**, a dependabot PR that reaches the job gets the
closing-line warning. Today that cannot happen — the job's `if:` skips any PR
touching `frontend/**` or `backend/**`, and every dependabot PR touches one of
them — so hunk 1 becomes load-bearing exactly when MEH-1949's hunk 2 lands. Apply
them together.

## 3 · What the script now does, shown failing against the old one

`.claude/rules/testing.md` § "Every new guard test must be shown failing": the
old script (the `origin/staging` blob) and the new one were run **end-to-end**
(title + body, no branch) over every fixture in
`.claude/scripts/test/fixtures/linear-mentions/`. Exit codes: `0` clean · `1`
bare identifier (rule 29) · `3` no standalone closing/chunk line (MEH-2244,
takes precedence when both apply).

| fixture | body carries | old exit | new exit | what the old script could not see |
|---|---|---|---|---|
| `clean` (existing) | prose, no identifiers | 0 | **3** | no closing line at all — the old scan had nothing to flag, so it passed |
| `closes-only` (existing) | `Closes: MEH-1379` | 0 | 0 | — |
| `bare-mention` (existing) | `Refs MEH-1377` | 1 | 3 | old flagged the bare mention; new adds "and no trailer" |
| `mixed` (existing) | `closes MEH-1200` + two bare mentions | 1 | 1 | — (trailer present; bare mentions still rule 29) |
| `valid-closes` | `Closes MEH-2244` | 0 | 0 | — |
| `valid-refs-chunk` | `Refs MEH-2244 (chunk 1/4)` | **1** | **0** | old **flagged the line the rule now requires** as a bare mention |
| `valid-closes-with-parent-refs` | `Refs MEH-2244` + `Closes MEH-2250` | 1 | 1 | trailer satisfied; the bare parent ref is still a rule-29 mention, unchanged |
| `closes-in-title-only` | title `closes MEH-100`, body nothing | **0** | **3** | old stripped the closing word from the title and saw a clean PR |
| `closes-in-parens` | `(closes MEH-1)` mid-sentence | **0** | **3** | old stripped `closes MEH-1` regardless of where it sat |
| `refs-without-chunk` | `Refs MEH-2244` | 1 | 3 | old exit 1 is the bare-mention reason — it never knew a suffix was missing |
| `dependabot` (author `dependabot[bot]`) | no identifiers | 0 | 0 | old exit 0 is "no identifiers", not an exemption; the new script names the skip |

**Discriminates:** the old rule-29 check is a *ban* — it strips every
`Closes|Fixes|Resolves MEH-N` wherever it appears and flags what is left. It has
no concept of a line, so it cannot tell "the closing word is in a parenthesis"
from "the closing word is the trailer", and it never looked for an *absence*.
The three bold rows are the ones the old script passes for the wrong reason
(`closes-in-title-only`, `closes-in-parens`) or fails for the wrong reason
(`valid-refs-chunk`).

**Existing behaviour preserved:** `--self-test` runs the four original text
fixtures and six branch cases through the same functions as before — `4 text
fixtures + 6 branch cases` pass identically before and after. End-to-end, the
only existing fixture whose verdict moved is `clean` (0 → 3), which is the new
rule doing its job on a body with no trailer. The single change to the rule-29
scan is that a **whole-line** `Refs MEH-<N> (chunk k/n)` is no longer a bare
mention — the gate cannot require a line and flag it in the same run (the
MEH-1949 collision shape). `bare-mention` and `refs-without-chunk` pin that a
suffix-less `Refs MEH-<N>` is still flagged.

Self-test, after: `4 text fixtures + 6 branch cases + 8 closing-line fixtures + 6
closing-line inline controls + 2 scan/chunk cases passed` (counts derived by the
script from its own arrays, not typed). The inline controls include the
negative control the card asks for — `(closes MEH-1)` in parentheses → FAIL —
paired with the same text minus the parentheses → PASS, so the parentheses and
not something else carry the verdict.

## 4 · Hunk 2 — making the closing-line rule block. Described, NOT applied

**This is Sapir's decision.** Rule 29's bare-mention scan stays warn-only either
way — the noise there is real (workflow.md rule 29b: `Refs` for human readers
is encouraged and is a bare mention by construction), and it was never meant to
block. The closing-line rule is different in kind: a body without a trailer is
never intentional, and the fix is one line the failure message spells out.

The script already separates the two by exit code, so blocking one and not the
other is a `case`, not a second script or a second run:

```diff
   linear-mentions:
-    name: Linear mention guard (rule 29, warn-only)
+    name: Linear mention guard (rule 29 warn-only · MEH-2244 closing line blocks)
     needs: changes
     if: ${{ needs.changes.outputs.frontend != 'true' && needs.changes.outputs.backend != 'true' && needs.changes.outputs.workflows != 'true' }}
     runs-on: ubuntu-latest
     timeout-minutes: 5
-    continue-on-error: true
     steps:
       ...
-      - name: Check for bare Linear identifiers (warn-only)
+      - name: Check bare Linear identifiers (warn-only) and the closing line (blocking)
         env:
           PR_AUTHOR: ${{ github.event.pull_request.user.login }}
-        run: bash .claude/scripts/check-linear-mentions.sh "$RUNNER_TEMP/pr_title.txt" "$RUNNER_TEMP/pr_body.txt" || true
+        run: |
+          rc=0
+          bash .claude/scripts/check-linear-mentions.sh "$RUNNER_TEMP/pr_title.txt" "$RUNNER_TEMP/pr_body.txt" || rc=$?
+          # 0 clean · 1 bare mention (rule 29 — warn-only, stays green)
+          # 2 invocation error · 3 no standalone Closes / Refs-chunk line (MEH-2244) — both red
+          case "$rc" in 0|1) exit 0 ;; *) exit "$rc" ;; esac
```

Three things this hunk does **not** do on its own, each a separate step for
Sapir, in this order:

1. **It does not run on the PRs it is for.** The job's `if:` skips every code PR
   (measured on #3292 and #3294 in the MEH-1949 doc, §"Phase 0 found a second
   gap"). A closing-line rule that only sees docs-only PRs checks the one class
   of PR that rule 29 already tells authors *not* to put identifiers in. Apply
   MEH-1949's **hunk 2** first; this hunk without it is a green that never ran.
2. **It does not make the job required.** Removing `continue-on-error` makes the
   *job* red; the *PR* is gated by the `CI gate` aggregator (`ci-gate`), and this
   job is not in its `needs:`. Promotion goes through the aggregator with the
   `check`/`check_ran` split (MEH-1582), never a direct required-check add — the
   MEH-892 skip-as-Expected trap. Same path §7 of the MEH-1844 history
   prescribes for the reviewer.
3. **It does not exempt the release PR.** A `staging → main` PR has `staging` as
   its head and no ticket to close. If those PRs run through this job after
   step 1 widens it, add `github.event.pull_request.head.ref != 'staging'` to the
   `if:` — the same carve-out the Branch name gate already makes.

Until step 2 is done, hunk 2 is a red job that blocks nothing — which is a
reasonable **calibration window**: it shows how many open PRs would have failed
before anything is enforced. Measure that number before promoting; do not
promote on the assumption it is small.

## 5 · Verifying the wiring discriminates

`--self-test` proves the script; these prove the **wiring**, which is all this
doc adds. A guard wired to nothing passes its own self-test perfectly.

1. **Hunk 1 fires.** A dependabot PR that reaches the job (only after MEH-1949
   hunk 2): the log must show `closing-line check SKIPPED — dependabot-authored
   PR`. If it shows the `::warning::MEH-2244 WARNING` line instead, the env var
   did not arrive.
2. **Hunk 1 does not over-fire.** A human-authored PR with no trailer: the log
   must show the `WARNING` line and the two expected lines. Without this row, a
   script that exempted everyone would pass step 1.
3. **Hunk 2 blocks the right rule.** A PR whose body has a bare `Refs MEH-<N>`
   *and* a `Closes MEH-<M>` line → exit 1 → job green. The same body with the
   `Closes` line removed → exit 3 → job red. Both, or the `case` is untested.

## 6 · What this does NOT do

- **It does not predict the close.** Rule 29b measured the same PR text closing
  a card on one merge and not on the next. The trailer says what the author
  *meant*; the post-merge `get_issue` flip-check stays mandatory.
- **It does not touch the rule-29 text scan's verdicts** beyond the whole-line
  chunk allowance in §3. A bare `Refs MEH-<parent>` above a `Closes MEH-<child>`
  is still reported as a mention (exit 1, warn-only today) — that is unchanged,
  and it is the reason `valid-closes-with-parent-refs` reads `1 → 1` in the
  table rather than `1 → 0`. Likewise an identifier in the **title** — e.g. a
  subject ending `(MEH-2244 chunk A)` — is still a rule-29 bare mention (exit
  1) even when the body's closing line is present; measured on this PR's own
  title/body, where the closing-line half reported OK and the title scan
  warned. Whether chunk subjects should name the card is a rule-29 question,
  not this gate's.
- **It does not add a second gate script.** The check is a third function in
  the existing file, sharing its `CLOSING` pattern, its fixture directory and
  its `--self-test`; one guard with three checks beats three guards sharing one
  input. `scripts/checks/run-all.sh` does not run this script — it discovers
  `scripts/checks/*.sh` only — so nothing there changes.
