## 3. Input validation

123 `Field(...)` constraints (`max_length`/`min_length`/`ge`/`le`/`pattern`)
across `schemas/schemas.py`. Free-text fields route through
`sanitize_text(value, max_length=...)` (bleach strip + length cap, MEH-329).
A `_min_letters_validator` (≥3 letter chars, MEH-555/MEH-772) guards
admin/public-facing free-text against punctuation-only spam — and the gaps
flagged in older docs (`ProducerCreate.name`, `HomeProductCreate.title`,
`ExperienceCreate.title`) are now closed (validators present at lines 291,
833, and the experience equivalent). LLM-facing `ChatMessage.content` is
bounded (`min_length=1, max_length=2000`) with `messages` capped at 40.

**Findings (LOW):**

| File | Line | Endpoint/Schema | Issue | Severity |
|---|---|---|---|---|
| schemas/schemas.py | 274–291 | ProducerCreate.name | Has `_min_letters_validator` (≥3 letters) but **no explicit `max_length`**. DB column is `String(200)` (models.py:46), so a >200-char name raises a DB error (500) instead of a clean 422. Robustness/defense-in-depth gap, not a breach. | LOW |
| schemas/schemas.py | 297 | ProducerAdminCreate.name | Same pattern — no `max_length` on `name`; admin-only surface so exposure is lower, but mirror the cap for consistency. | LOW |

All other request schemas reviewed (HomeProductCreate, ExperienceCreate,
ContactIn, ChatRequest, ChatMessage, NewsletterIn) are bounded.

## 6. File upload

`routers/upload.py` reviewed in full.

**No findings.** Controls confirmed:
- Auth required (`Depends(get_current_user)`) on both `/image` and `/avatar`.
- Size enforced first (`read(MAX_FILE_SIZE + 1)`, 5 MB cap) — fails cheaply, no OOM.
- Empty-file rejection.
- **Magic-byte sniff** (`_sniff_image_type`, JPEG/PNG/WebP/GIF signatures) — client `Content-Type` is NOT trusted.
- Cloudinary `public_id = uuid4().hex` (not user filename); `resource_type="image"` adds a server-side second check.
- Rate-limited (`20/hour`, `10/hour`).
- Freemium gate (3 images, free producers) enforced server-side.

| File | Line | Endpoint/Schema | Issue | Severity |
|---|---|---|---|---|
| routers/upload.py | 35–119 | POST /upload/image | Magic-byte + size + UUID + auth all present | — none |
| routers/upload.py | 129–200 | POST /upload/avatar | Same controls; fixed per-user public_id | — none |

## 7. CORS

`middleware.py:214–218` configures `CORSMiddleware`.

**No findings.**
- `allow_origins = settings.cors_origins_list()` — explicit allowlist from
  `CORS_ORIGINS` env, **not** a wildcard.
- Default (`config.py:43`) is localhost-only (`http://localhost:3000,:8000`)
  — production MUST set `CORS_ORIGINS` explicitly (deploy requirement, noted
  in config comment).
- `allow_credentials=True` is paired with an explicit origin list (no
  wildcard+credentials combo, which browsers reject anyway).
- Methods/headers are explicit allowlists (`GET/POST/PUT/DELETE/OPTIONS`;
  `Authorization`, `Content-Type`, ...).

| File | Line | Endpoint/Schema | Issue | Severity |
|---|---|---|---|---|
| middleware.py | 214–218 | global CORS | Explicit origin allowlist + credentials, no wildcard | — none |

Residual operational note (not a code finding): if `CORS_ORIGINS` is left
unset in production, the localhost default would block the real frontend —
a fail-safe (deny) direction, not a security hole.

## 8. JWT

`auth.py` (joserfc), `config.py` settings, `middleware.py` Sentry context,
`services/oauth_verifiers.py` OAuth.

**No findings.**
- Algorithm pinned `HS256` (`config.py:28`); decode uses an explicit
  allowlist `algorithms=[settings.algorithm]` (`auth.py:85, 213`;
  `middleware.py:164`) — **alg=none is rejected** (not in allowlist).
- OAuth verifier pins `algorithms=["RS256"]` for Google/Apple JWKS
  (`oauth_verifiers.py:201`).
- Secret loaded from env (`JWT_SECRET_KEY`/`SECRET_KEY`); production
  fail-fast if unset.
- Expiry set: 15-min access token + 14-day refresh with rotation
  (`config.py:35–36`, MEH-326). Fingerprint binding (`__Secure-Fgp`,
  MEH-327) defends token sidejacking.

| File | Line | Endpoint/Schema | Issue | Severity |
|---|---|---|---|---|
| auth.py | 85, 213 | token decode | Explicit `algorithms=[HS256]` allowlist — no alg=none | — none |
| config.py | 28, 35–36 | JWT config | HS256, 15min access / 14d refresh, env secret | — none |
| oauth_verifiers.py | 201 | OAuth verify | RS256 pinned for external JWKS | — none |

## Top 5 pre-launch

Backend security posture is strong; there are no CRITICAL/HIGH items to gate
launch. The list below is ordered by what would most improve robustness, plus
the two deploy-config reminders that, if missed, would cause an outage or
expose a gap.

1. **Set `CORS_ORIGINS` explicitly in production** — `config.py:43`. Default
   is localhost-only; production deploy MUST set the real frontend origin(s).
   (Deploy-config, not a code defect — fail-safe deny direction.)
2. **Set `JWT_SECRET_KEY` in production** — `config.py:25–27` /
   `docs/SECURITY.md` §1. App fail-fasts if unset; verify it is present in
   Railway prod + staging before launch.
3. **Add `max_length=200` to `ProducerCreate.name`** — `schemas/schemas.py:275`.
   Currently relies on `_min_letters_validator` + the `String(200)` DB column
   (`models.py:46`); without the Pydantic cap a >200-char name returns 500
   instead of 422. LOW.
4. **Add `max_length` to `ProducerAdminCreate.name`** — `schemas/schemas.py:297`.
   Same gap on the admin surface; mirror the cap for consistency. LOW.
5. **Confirm `TRUSTED_PROXY=1` on Railway** — `docs/SECURITY.md` §2 /
   `rate_limit.py`. Without it, the rate-limiter falls back to the proxy IP and
   collapses every user into one bucket, silently weakening every limit above.
   (Deploy-config — verify, not a code defect.)
