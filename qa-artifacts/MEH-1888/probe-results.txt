2 · A SECOND, NARROWER LOSS — found, measured, reported not fixed
-----------------------------------------------------------------
`.loose()` applies to the TOP LEVEL ONLY. Nested z.object schemas
(categories[], delivery_areas[], locations[], active_offer) still strip
their own undeclared keys. A deep raw-vs-parsed diff over the full
payload found exactly one such key:

  LOST  producer.categories[0].producer_count = null

Consumer check before calling it harmless: `producer_count` is read at
frontend/app/[locale]/admin/content/page.js:93, :164, :200 — the admin
categories screen, fed by GET /categories, NOT by this route. Nothing
in the producer-page tree reads it. So this loss is inert TODAY, and it
is a live example of the same mechanism one level down.

Not fixed here: making the nested objects loose means editing
lib/schemas.js, which is outside this ticket's file_locations (the hook
and its test). Reported so it is a known gap with a name rather than a
surprise.

4 · AN ANOMALY DURING QA — explained, not waved away
----------------------------------------------------
An intermediate capture reported 1394/1471 chars against 1491/1568,
which read as "the parse dropped ~97 characters". It did not. That run
hit a `next start` process whose .next directory had been overwritten by
a later build while it was still serving — the new `next start` had
failed with EADDRINUSE, so the old server stayed up and answered from a
half-replaced build. Two things establish this rather than assert it: a
repeat capture against the SAME server returned a byte-identical PNG (so
the harness is deterministic), and the controlled pair above — built and
served with the port verified free between phases — is byte-identical in
both directions.

Recorded per the Bug Protocol: an anomaly seen during QA is explained or
reported, never attributed to the harness and dropped. Here it WAS the
harness, and this is the evidence for saying so rather than the excuse.
